## 목표

기업이 분기 실적을 발표할 때 **EPS·순이익·매출의 전년동기(YoY) 성장**을 확인하고,
주가가 **아직 더 오를 여력(가격 모멘텀)** 이 있으면 매수해, **과거 드리프트 기댓값으로 추정한 동적 목표가**에 매도하는 전략(PEAD)을 검증한다.

핵심 질문: *KOSPI에서 "좋은 실적 + 상승 추세" 종목을 발표 후 따라 사면, 비용·생존편향을 정직하게 차감한 뒤에도 양의 기대값(알파)이 남는가?*

> PEAD(Post-Earnings Announcement Drift): 좋은(나쁜) 실적 발표 후 주가가 즉시 완전 반영되지 않고 수 주~수십 거래일에 걸쳐 같은 방향으로 표류하는 잘 알려진 이상현상. 단, 공개·연구된 알파라 **시대별 감쇠(alpha decay)** 가 보고됨 — `docs/research/04-smallcap-lowpbr-alpha-decay.md` 참조.

## ⚠️ 가장 중요한 발견: 엔진 구조 미스매치 → 검증을 3모드로 분리

기존 백테스트 엔진은 **단일 종목·단일 롱/플랫 포지션·전액투입·OHLCV-only 인터페이스**다
(`engine/src/trading_engine/backtest/engine.py:66-159`, `strategy/base.py:31`). PEAD는 본질적으로
**여러 종목이 동시에 신호를 내는 횡단면(cross-sectional) 이벤트 전략**이라 정면 충돌한다.
이 충돌을 인정하고 검증을 3모드로 분리해 정직성을 확보한다:

| 모드 | 방식 | 엔진 사용 | 1차 범위 | 목적 |
|------|------|-----------|----------|------|
| **A. 이벤트 스터디** | 진입+1 시가 대비 N일 누적초과수익(CAAR, 시장 대비) 집계. 백테스트 엔진 미사용 | ❌ | ✅ 포함 | **알파 존재 여부 1차 GO/NO-GO** (편향 최소) |
| **B. 종목별 단일 포지션** | 종목마다 기존 엔진 `run()` 재사용 | ✅ | ✅ 포함 | 비용 차감 후 **종목별 수익률 분포** 확인 |
| **C. 진짜 포트폴리오** | 동시 보유·자본배분·신호 우선순위 → 엔진 재작성 | (재작성) | ❌ 제외 | 알파 확인 후 별도 phase |

> ⚠️ **모드 B 정직성 규칙**: 엔진은 종목마다 `qty = cash / price`로 전액투입(`engine.py:117`)이라
> N종목 수익률을 합산하면 자본이 N배로 뻥튀기된다. **포트폴리오 수익률을 주장하지 않고**,
> 종목별 수익률 분포(중앙값·IQR·승률)만 보고한다.

## 데이터 리스크 → Phase 0 Spike 먼저 (NO-GO 게이트)

가격 데이터(FDR)와 달리 실적·유니버스 데이터는 입수·정합성이 어렵다. 구현 전 반드시 검증한다:

1. **Point-in-time(접수일 기준)** — 재무 수치는 **공시 접수일(rcept_dt, 보통 분기말+45~90일)** 에야 시장이 안다. 분기말 기준으로 인덱싱하면 45~90일 룩어헤드. 신호 가용일은 반드시 **DART 접수일** 기준.
2. **정정공시·잠정 vs 확정** — 최초 잠정실적 후 정정으로 숫자가 바뀜. 백테스트는 **최초 접수 시점의 최초 숫자**로 신호를 내야 함(정정 후 확정치 사용은 룩어헤드). 진입 트리거 공시 유형을 **단일 정의**.
3. **컨센서스 부재** — 무료 소스(DART)엔 애널리스트 추정치가 없음 → "서프라이즈" 대신 **YoY 성장**으로 대체(사용자 결정).
4. **생존편향 (NO-GO 가능 사유)** — `FdrProvider.load_daily`는 생존 종목만 조회(`fdr_provider.py:23`). 상장폐지 종목이 빠지면 "실적 쇼크 후 폭락→상폐" 표본 누락 → 결과 과대평가. **상폐 포함 point-in-time 유니버스** 확보 가능 여부가 핵심.

→ Phase 0에서 GO/NO-GO 판단 후 사람 승인을 받고 Phase 1+에 들어간다.

## 핵심 설계 결정 (이유 포함)

1. **검증을 모드 A→B로 한정, C는 제외** — 단일 포지션 엔진(`engine.py`)으로 다종목 PEAD를 흉내내면 거짓 수익률이 나온다. 알파 존재는 엔진 없는 이벤트 스터디로 먼저 확인하는 게 가장 정직하다. (analyst 최우선 권고)

2. **재무 feature는 OHLCV 인터페이스에 욱여넣지 않고 별도 파이프라인** — `base.py:31`의 OHLCV-only 계약을 깨지 않기 위해, 재무 데이터는 `earnings.py`에서 **신호 가용일 기준 feature**로 사전계산해 전략 생성자에 주입한다. 전략은 그 feature를 df.index에 PIT 정렬해 signal Series를 만든다.

3. **신호 = YoY 성장 + 가격 모멘텀** (사용자 결정, 무료 데이터 친화):
   - 진입: `EPS YoY ≥ 임계` (그리고/또는 순이익·매출 YoY) **AND** 접수일+1 종가 > SMA(예: 60일).
   - 복수 지표 결합(AND/OR/가중) 규칙을 **사전 고정**(p-hacking 차단). 1차는 EPS YoY 단일 + SMA 필터로 단순하게.

4. **청산 = 과거 드리프트 기댓값 동적 목표가, 1차는 (a) next-open 근사** (사용자 결정 + analyst Q1):
   - 전략은 실제 체결가(`effective_buy_price(next_open)`, `engine.py:115`)를 모름 → 목표가는 **신호 다음 봉 시가 추정치 × (1 + 기대드리프트)** 로 근사. 한계(슬리피지·갭 미반영)를 명시.
   - 도달 판정은 **룩어헤드 없는 종가 트리거**: 종가가 목표 초과 → 그 다음 봉 시가 청산.
   - **⚠️ expanding window**: 기대드리프트는 반드시 **진입일 이전 이벤트만**으로 추정(전체표본 평균=룩어헤드).
   - 정확도가 결론을 바꿀 만큼 중요해지면 (b) 엔진 확장으로 승격(별도 결정).

5. **필수 가드레일** (미정의 시 결과 오염 — analyst):
   - **최대 보유기간 time-stop** (예: 60거래일) — 목표가 미도달 시 강제 청산. 없으면 무한 보유.
   - **최소 표본 수** (예: 누적 이벤트 ≥ 30~50) 미만이면 드리프트 추정 불가 → 거래 보류.
   - **목표 드리프트 클램프** (예: 0~20%) — 노이즈 폭주 방지. 음의 드리프트 버킷이면 진입 스킵.
   - **유동성 필터** — 최소 일평균거래대금/동전주 제외. `costs.py:17`의 5bp 슬리피지는 대형주 가정이라 소형주엔 비현실적.

6. **드리프트 추정 버킷·OOS 사전 고정** (analyst Q4):
   - 버킷(성장분위/섹터/서프라이즈 크기)을 **사전 고정**하고 robustness만 사후 점검. 1차는 단순 버킷(전체 또는 성장률 분위).
   - 진입/청산 파라미터 조합은 수백 개 → **OOS/walk-forward 분리** 또는 사전등록 파라미터만 검증.
   - 드리프트 기댓값(평균) 외 중앙값/도달확률도 후보 — 사용 통계량 명시.

7. **비용 모델: 개별주 매도거래세 0.18% 기본 적용** — `costs.py:18`의 `sell_tax_rate` 기본 0은 ETF 가정. PEAD는 개별주이므로 **0.0018**로 설정. 왕복 비용 ≈ 0.21%+슬리피지를 넘는 드리프트여야 생존.

8. **벤치마크 명시** — 초과수익은 KOSPI 지수(또는 동일섹터) 대비로 정의. 미정의 시 "알파" 주장 불가.

## 검증 방법

- **모드 A (알파 게이트)**: 진입+1 기준 N일 CAAR(시장 대비)이 통계적으로 유의(예: t>2) **그리고** 비용 추정 차감 후 양수.
- **룩어헤드 회귀 테스트**: 모든 신호 가용일 = DART 접수일+1 이상임을 단위테스트로 보장(분기말 기준 인덱싱 금지). 정정공시 시 **최초 숫자 고정** 검증.
- **합성 데이터 단위 테스트**: 알려진 실적·가격 시퀀스 → 예상 진입/청산/손익. YoY 계산, PIT join, 동적 타깃 expanding window(미래정보 미유입), time-stop 동작.
- **비용 회귀 테스트**: 매도세 0.0018 적용 확인.
- **실데이터**: 소수 대표 종목(삼성전자·SK하이닉스 등) → 유니버스 확대. 결과 합리성 점검.
- 기존 워크플로우대로 **"실행해서 확인"** 후 결과를 본 문서 상단에 기록(WORKFLOW.md 규칙 3).
